# Backend Architecture (Kotlin, offline sync)

> **MVP — аутентификация:** только **саморегистрация по паролю** (`POST /api/v1/auth/register` + login). **Внешние SSO / OAuth в MVP не используются** (ни в API, ни в мобильном клиенте).

## Цели
- REST API для мобильного клиента (foreman, admin).
- Парольная **саморегистрация** и авторизация (см. выше).
- Смены (старт/стоп): **только через `POST /api/v1/sync/batch`** — при появлении сети клиент отправляет накопленные батчи **в строгом порядке очереди** (head-of-line), с идемпотентностью по `batch_uid`. Отдельных REST‑эндпоинтов «старт/стоп смены» **нет**.
- Рабочие: **только онлайн** (GET/POST/PATCH), **в батчи не входят**; отдельной офлайн‑очереди на добавление рабочего **нет**.
- **Единственный отчёт для ADMIN (MVP):** за **предыдущий календарный день** — по **каждой** записи из `workers` (**все работники, включая бригадира** как отдельную карточку): суммарные **часы** и **эквивалент смен**, где **1 смена = 8 часов** (например 9 ч → **1,125** смены).
- Простая схема **access/refresh JWT** (ниже — отдельный раздел про токены).

### Объём MVP (обязательный минимум)
- Авторизация (**только password**, саморегистрация) и роли USER/FOREMAN/ADMIN. Создание пользователя админом (`POST /users`) **не входит в MVP** — учётные записи появляются только через **register**.
- Рабочие **только при наличии сети**: GET/POST/PATCH `/workers` — без офлайн‑батчей и без очереди на добавление рабочего.
- Смены: **исключительно** события `START_SESSION` / `END_SESSION` внутри **`POST /api/v1/sync/batch`** (и онлайн, и офлайн на клиенте сводятся к очереди батчей; порядок отправки фиксирован).
- Отчёт: **GET** с агрегацией часов и долей смены (норма 8 ч) по **всем** строкам `workers` за **вчера** (см. ниже).
- JWT access + refresh, хранение refresh в PostgreSQL (MVP).

## Технологический стек
- **Kotlin + Ktor** (Netty/CIO) — HTTP‑сервер на корутинах.
- **PostgreSQL** — основное хранилище.
- **Exposed / JDBC** — доступ к БД (через `suspend`/`withContext(Dispatchers.IO)`).
- **JWT** (access/refresh) через `ktor-server-auth-jwt`, Bean Validation по необходимости.
- **Flyway** — миграции схемы.
- **Redis** (опционально) — сессии/refresh‑токены/кэши в проде; не обязателен для первого запуска.
- **Тесты**: JUnit 5 + Testcontainers.
- **Документация**: OpenAPI/Swagger (через ktor‑плагины или отдельную спека).

## Слои
- api: контроллеры + фильтры безопасности.
- domain: сервисы, бизнес-правила, DTO.
- data: репозитории, транзакции, маппинги, миграции.
- utils: инфраструктурные утилиты (время, токены, общие helper’ы).

## Доменные роли

- USER: базовая роль после регистрации. Может только авторизоваться и видеть свой профиль/ограниченную информацию, но не управлять рабочими и сессиями.
- FOREMAN: старт/стоп смен **только через отправку батчей** (`sync/batch`); рабочие — только онлайн (`/workers`).
- ADMIN: просмотр/редактирование пользователей (роли, блокировка), все рабочие, **отчёт за вчера** (часы + эквивалент смен по 8 ч по всем `workers`, включая бригадиров); создания пользователя без register — **нет**.

### Поведение ролей при регистрации

- **Саморегистрация** (`POST /api/v1/auth/register`):
  - Новый пользователь создаётся с ролью **USER**.
  - Пока ADMIN явно не повысит его до FOREMAN, он не может стартовать/закрывать смены и управлять рабочими.

- **Выдача роли бригадира админом** (`PATCH /api/v1/users/{id}` или отдельный админский эндпоинт с тем же смыслом):
  - Когда админ устанавливает пользователю роль **`FOREMAN`**, backend **в той же транзакции** создаёт запись в **`workers`** (или дополняет существующую по `workers.user_id`, если политика допускает повторный выход «в бригадиры»), чтобы у аккаунта появился **`worker_id`** для собственных смен. См. раздел «Связь FOREMAN ↔ worker».

- **Понижение с роли бригадира** (админ меняет роль `FOREMAN` → `USER` или другую, кроме повторного `FOREMAN`):
  - **Подчинённые рабочие:** у пользователя могут быть карточки в `workers` с `foreman_id = этот пользователь` (его «команда»). В MVP разумно **не допускать** понижение, пока существует хотя бы один **активный** такой рабочий **кроме** собственной карточки бригадира (та же строка, где `workers.user_id = users.id`). В ответ — **409 Conflict** с понятным `reason` и, по возможности, списком `worker_id`, которых нужно сначала **переназначить** другому `FOREMAN` через `PATCH /api/v1/workers/{id}` (смена `foreman_id`).  
    - *Опционально позже:* в одном админском запросе передавать «передать всех рабочих бригадира X бригадиру Y» — тогда понижение выполняется в одной транзакции после массового обновления `foreman_id`.
  - **Собственная карточка бригадира** (строка `workers` с `user_id = users.id`): выставить **`workers.status = INACTIVE`**, **`user_id = NULL`** (аккаунт больше не привязан к карточке; история сессий по `worker_id` сохраняется). Имена в строке можно не трогать или синхронизировать с `users` при следующем повышении — на усмотрение реализации.
  - **Активные смены:** закрыть все **`sessions` со `status = ACTIVE`**, где **`sessions.foreman_id = id` этого пользователя** (и смены подчинённых, и своя смена бригадира): `end_at` и `status = CLOSED` по правилу как при деактивации рабочего (см. примечания к данным; время закрытия — политика: серверное `now()` или явное правило в доке — для консистентности с офлайн лучше зафиксировать **серверное `now()`** при админском действии).
  - **Токены:** отозвать все **refresh**‑токены этого пользователя (и при необходимости инвалидировать сессии), чтобы старый JWT с ролью `FOREMAN` не жил до `exp` без контроля.

- **Увольнение / блокировка пользователя** (админ выставляет `users.status = INACTIVE` или аналог «заблокирован»):
  - Если у пользователя когда‑либо была роль **`FOREMAN`** или она ещё активна — применить **те же правила**, что и при понижении: сначала **переназначить** чужих рабочих с его `foreman_id`, закрыть активные сессии с его `sessions.foreman_id`, деактивировать и отвязать собственную карточку `workers` (`user_id = NULL`), затем выставить `users.status` и отозвать refresh‑токены.
  - Логин для `INACTIVE` — **401** / отказ в выдаче токенов (как уже подразумевается проверкой статуса при логине).

- **Защита «последнего администратора»** (чтобы не потерять доступ к управлению системой):
  - Если в БД **ровно один** активный (`status = ACTIVE`) пользователь с ролью **`ADMIN`**, то запрещено выполнять действия, после которых **не останется ни одного** такого пользователя: снятие роли `ADMIN`, перевод в `USER`/`FOREMAN`, установка `INACTIVE`.
  - В ответ — **409 Conflict**, `reason` вроде `last_admin_protected`.
  - *Смысл:* иначе через API больше **некому** выдавать роли и разблокировать пользователей — восстановление только **вручную в БД**. Это не отдельный тип учётки, а **бизнес‑правило** на уровне PATCH пользователя.

## Основные сущности (БД) — минимальный набор
- users: авторизация/роль. Идентификаторы — `UUID` (как в БД, так и во внешнем API).
- workers: карточки рабочих. Идентификаторы — `UUID`. Для связи с аккаунтом и назначением:
  - `workers.user_id` (nullable) связывает пользователя (например FOREMAN) и его карточку рабочего;
  - `workers.foreman_id` определяет текущего бригадира-владельца карточки (для списка «Мои рабочие» и переназначения);
  - имя хранится как **`first_name` + `last_name`** (обязательные поля, по аналогии с `users`); опционально **`position`** (должность для отображения в списках).
- sessions: рабочие сессии (start/end), статус. Идентификаторы — `UUID`.
- sync_batches: хранятся **только успешно применённые** батчи (для идемпотентности). При ошибке транзакция откатывается, запись не создаётся; успех/конфликт выражаются HTTP-кодом (200 vs 409), не полем в БД.
- sync_events: события внутри батча **только по сессиям** — START_SESSION, END_SESSION (добавление/редактирование/деактивация рабочих в батч не входят, только через онлайн API).
- failed_sync_batches: копии батчей, которые не удалось применить (409 Conflict). Нужны, чтобы не терять «кривой» батч: пользователь может позже посмотреть его (в т.ч. с другого устройства), отредактировать и отправить заново. См. ниже раздел про сохранение неуспешных батчей.

> Таблица audit_log, а также явная сущность devices и дополнительные аналитические/диагностические поля исключены из MVP для упрощения модели. При необходимости они могут быть добавлены отдельной миграцией позже.

## Валидация и конфликты
- Идемпотентность: один уникальный `batch_uid` на батч (клиент генерирует UUID при создании батча; при повторе запроса отправляет тот же `batch_uid` — сервер не применяет батч повторно).
- Применение батча — атомарно в транзакции (только события сессий).
- Конфликты в батче: например, сессия уже закрыта на сервере или worker_id не найден/деактивирован; возвращается **409 Conflict**, в теле — детали и при необходимости актуальные версии сущностей. Управление рабочими в батчах нет — конфликты «параллельное добавление/удаление рабочего» не возникают.
- Версионирование: при необходимости — поля version/updated_at для оптимистических проверок по сессиям.

## Аутентификация и сессии
- Password flow: email/phone + `first_name`/`last_name` + пароль → JWT (access/refresh).
- Хранение refresh‑токенов:
  - MVP: хранить refresh‑токены в PostgreSQL (отдельная таблица tokens или в users).
  - Прод: при необходимости вынести в Redis.

### Auth-flow без отдельного сервера авторизации

Для MVP авторизация реализована внутри нашего Ktor backend’а (без отдельного auth‑сервера):

- **Регистрация (`POST /api/v1/auth/register`)**
  - Вход: email/phone, `first_name`, `last_name`, пароль.
  - Бэкенд:
    - валидирует входные данные;
    - хеширует пароль (BCrypt/Argon2);
    - создаёт запись в `users` с ролью `USER` и статусом `ACTIVE`;
    - опционально сразу возвращает access/refresh токены (или предлагает явный логин).

- **Логин (`POST /api/v1/auth/login`)**
  - Вход: email/phone + пароль.
  - Бэкенд:
    - ищет пользователя в `users` по email/phone, проверяет статус `ACTIVE`;
    - сравнивает пароль с `password_hash`;
    - выдаёт:
      - **access JWT** (короткий срок жизни, сейчас 60 минут) с полями: `sub` (userId), `role` (`USER`/`FOREMAN`/`ADMIN`), `exp`;
      - **refresh‑токен** (долгоживущий opaque‑строка), который хранится в БД (таблица `tokens` или поле в `users`) c привязкой к userId, датам создания/истечения и возможностью отзыва.

- **Обновление токена (`POST /api/v1/auth/refresh`)**
  - Вход: refresh‑токен.
  - Бэкенд:
    - проверяет, что токен существует, не истёк и не отозван;
    - выдаёт новый access JWT (опционально — новый refresh‑токен, старый помечает как отозванный/истёкший);
    - при любом подозрении/компрометации удаляет все refresh‑токены пользователя.

- **Выход (`POST /api/v1/auth/logout`)**
  - Бэкенд инвалидирует текущий refresh‑токен (или все токены пользователя, в зависимости от политики), access‑токен истекает сам по `exp`.

### JWT access и refresh (контракт для сервера и клиента)

**Access JWT**
- Короткий срок жизни (сейчас **60 минут**), передаётся в каждом запросе: `Authorization: Bearer <access_jwt>`.
- Содержимое (claims): минимум **`sub`** = `userId` (UUID), **`role`** = `USER` | `FOREMAN` | `ADMIN`, **`exp`**, при необходимости **`iat`**. Дополнительные поля — по мере необходимости.
- Подпись: симметричный ключ (HMAC) или асимметричный — на выбор деплоя; секрет/ключи **не** попадают в клиент (кроме проверки на сервере).
- **Нет отзыва по одному access:** пока не истёк `exp`, токен формально валиден. Поэтому при смене роли, блокировке или компрометации критично **отозвать refresh** и полагаться на короткий TTL access.

**Refresh токен**
- Не JWT (рекомендуется **opaque** случайная строка), длинный срок жизни (дни/недели — политика продукта).
- Хранение на сервере: таблица `refresh_tokens` (или аналог) с полями `user_id`, `token_hash` (хранить хеш, не сырую строку), `expires_at`, `revoked_at`, `created_at`.
- В ответах login/refresh отдавать refresh **только в теле** (или в httpOnly cookie, если когда‑нибудь понадобится web); в мобильном приложении — **EncryptedSharedPreferences** / DataStore, не в логах.

**Обновление access (`POST /api/v1/auth/refresh`)**
- Тело: refresh токен (как договоритесь в API, например `{ "refreshToken": "..." }`).
- Успех: новый access JWT; опционально ротация refresh (новый refresh, старый помечен отозванным).
- Ошибка: невалидный/истёкший/отозванный refresh → **401**; клиент должен направить пользователя на **повторный логин**.

**Клиент (Retrofit / OkHttp): рекомендуемый interceptor**
1. Запросы с access в заголовке.
2. При ответе **401** на защищённом эндпоинте (кроме самого refresh): **один** запрос `POST /api/v1/auth/refresh` с сохранённым refresh (с блокировкой/мьютексом, чтобы не устроить «шторм»).
3. Успех refresh → подставить новый access, **повторить исходный запрос** один раз.
4. Неуспех refresh → очистить токены, экран логина.

**Когда сервер отзывает refresh**
- `logout`; смена роли или `INACTIVE` (см. раздел про роли); смена пароля (если появится); подозрение на утечку — «отозвать все refresh пользователя».

**Безопасность**
- Пароли и refresh в логах **не** писать; access в логах клиента — не логировать целиком.

- **Авторизация в API**
  - Все защищённые эндпоинты требуют заголовок `Authorization: Bearer <access_jwt>`.
  - Фильтр безопасности:
    - валидирует подпись и срок действия JWT;
    - извлекает `userId` и `role`;
    - навешивает ограничения:
      - `FOREMAN`: `GET/POST/PATCH /workers` (свои рабочие в рамках прав), **`POST /api/v1/sync/batch`**; отчётов в MVP **нет**; **изменения смен не через отдельные `/sessions/*`** — таких маршрутов нет.
      - `ADMIN`: `GET/PATCH /users`, `GET/POST/PATCH /workers`, **GET отчёта**, при необходимости `GET /sync/failed-batches` для поддержки;
      - `USER`: только свой профиль / минимальный read (`/users/me` и т.п.).

## Черновик API (namespace `/api/v1`)
- **Auth:** `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`.  
  Регистрация — **единственный** способ появления новой учётной записи в MVP (без `POST /users` от админа).

- **Users (ADMIN + self):** `GET /api/v1/users`, `PATCH /api/v1/users/{id}`, `GET /api/v1/users/me`.  
  **`POST /api/v1/users` в MVP не используется** (создание только через register).  
  При смене роли на **`FOREMAN`** через `PATCH` backend **в той же транзакции** создаёт/обеспечивает строку в **`workers`**.  
  При **снятии** `FOREMAN` / **`INACTIVE`** — см. раздел «Поведение ролей» и правило **последнего админа**.

- **Workers (только онлайн, без батчей):**
  - `GET /api/v1/workers` — `FOREMAN`: «мои» (`foreman_id = userId`); `ADMIN`: все (или с фильтрами).
  - `POST /api/v1/workers` — создать карточку (только при наличии сети; тело: `first_name`, `last_name`, опционально `position`); `foreman_id` = текущий `FOREMAN` из JWT (для админа — уточнить в реализации: передать `foreman_id` в теле или только от имени выбранного бригадира).
  - `PATCH /api/v1/workers/{id}` — в MVP: **переназначение** другому `FOREMAN` (`foreman_id`) и/или **деактивация/активация** (`status`). **Редактирование ФИО/должности в MVP не делаем** (отдельная задача позже).

- **Смены:** отдельных `POST /sessions/start|end` **нет**. Любое открытие/закрытие смены — только события в **`POST /api/v1/sync/batch`**.  
  Опционально позже: read-only `GET` для сверки состояния (например активные смены) — не обязателен, если клиент достраивает UI из локального кэша после успешных батчей.

- **Sync:** `POST /api/v1/sync/batch` — единственная точка применения `START_SESSION` / `END_SESSION`.  
  Опционально: `GET/DELETE /api/v1/sync/failed-batches` — как в разделе про неуспешные батчи.

- **Отчёт (ADMIN), единственный в MVP:** `GET /api/v1/reports/hours-by-worker-previous-day`  
  - По умолчанию отчётный день — **вчера** относительно календарной даты сервера (timezone зафиксировать в конфиге, например UTC или `Europe/Moscow`).  
  - Опциональный query `?date=YYYY-MM-DD` — тот же тип отчёта, но за указанный **завершённый** календарный день (для отладки; в UI MVP достаточно «вчера»).  
  - **Состав строк:** в ответе — **каждая** подходящая запись из `workers` (например `status = ACTIVE`; политику для `INACTIVE` зафиксировать — обычно показывать с нулями или исключать). **Обязательно включать** строку бригадира: у пользователя с ролью `FOREMAN` после выдачи прав есть своя строка в `workers`, и её часы/смены за день считаются так же, как у остальных.  
  - **Часы:** для каждого `worker_id` суммировать длительность **закрытых** смен (`status = CLOSED`), у которых **`end_at` попадает в выбранный календарный день** (в TZ сервера): `hours = sum(end_at - start_at)` в часах (десятичная дробь). Нет закрытых смен за день → `hours = 0`.  
  - **Эквивалент смен:** норма **8 часов = 1 смена** (константа MVP, при необходимости позже вынести в конфиг). `shiftEquivalent = hours / 8` (то же число, что 9 ч → 1,125). В JSON — число с плавающей точкой; округление отображения на клиенте (например до 3 знаков).  
  - Ответ (пример):  
    ```json
    {
      "reportDate": "2025-03-04",
      "timezone": "Europe/Moscow",
      "shiftNormHours": 8,
      "rows": [
        {
          "workerId": "uuid",
          "firstName": "Иван",
          "lastName": "Петров",
          "foremanId": "uuid",
          "foremanDisplayName": "Михаил Зотов",
          "hours": 9.0,
          "shiftEquivalent": 1.125
        }
      ],
      "totals": { "hours": 24.5, "shiftEquivalent": 3.0625 }
    }
    ```  
  - Поля `foreman*` — для отображения «чей подчинённый»; для строки самого бригадира допускается `foremanDisplayName` = он же или null — зафиксировать в реализации единообразно.  
  - Права: только **`ADMIN`**.

## HTTP-статусы (RESTful)

Используем стандартные коды ответа:

- **2xx — успех:** 200 OK (успешное применение батча, получение ресурса, идемпотентный повтор), 201 Created (создание ресурса, где уместно).
- **4xx — ошибка клиента:** 400 Bad Request (невалидное тело запроса, например батч слишком большой), 401 Unauthorized (нет или неверный токен), 403 Forbidden (нет прав), 404 Not Found (ресурс не найден), **409 Conflict** (батч не применён из‑за бизнес-конфликта: сессия уже закрыта, worker не найден и т.п.).
- **5xx — ошибка сервера:** 500 Internal Server Error; при сетевых/временных сбоях клиент может повторять запрос (ретраи).

Для **POST /sync/batch** в частности:
- **200 OK** — батч применён (или уже был применён при идемпотентном повторе). В теле — созданные/обновлённые сессии для обновления локального кэша.
- **409 Conflict** — батч не применён из‑за конфликта при обработке одного из событий. В теле: `failedEventIndex`, `reason`, при необходимости `failedEventType`, `payload`, актуальное состояние сущности.
- **400 Bad Request** — невалидный запрос (например, превышен лимит размера батча, некорректный JSON).
- **401 Unauthorized** — не авторизован.
- **5xx** — внутренняя ошибка сервера; клиент может ретраить.

## Логирование и отладка батчей

Для упрощения отладки и поиска багов при небольшом количестве запросов логируем батчи достаточно подробно.

### Что логируем

- Для каждого `POST /sync/batch`:
  - `INFO`‑лог: `timestamp`, `userId`, `batchUid`, `eventsCount` (и, при необходимости, первые 1–2 события по типу/workerId).
  - `DEBUG`‑лог (на dev/stage или по фиче‑флагу) — **полный JSON‑payload** запроса (`events[]`), чтобы можно было воспроизвести и проанализировать ошибку.
- При ошибках:
  - `ERROR`‑лог: `userId`, `batchUid`, HTTP‑код (500/409), `errorMessage`, stacktrace, при необходимости — усечённый payload (первые N символов JSON).

### Где и как храним логи

- Формат логов — **структурированный JSON** (Logback/Log4j2 + JSON encoder), чтобы можно было легко искать по `batchUid`/`userId`.
- Логи пишутся в файл (и/или stdout) с ротацией:
  - rolling‑policy по размеру/времени (например, 100MB × 10 файлов), старые файлы архивируются/удаляются.
- На старте достаточно поиска по файлам (`grep`/`rg` по `batchUid`); при росте проекта можно добавить стек сбора логов (Loki/ELK), используя уже структурированный формат.

### Безопасность

- Не логируем чувствительные данные:
  - токены, пароли и т.п. никогда не попадают в логи.
  - если в `events` есть приватные поля (например, произвольные комментарии), полный payload логируется **только** в dev/stage или под флагом «расширенный лог», на проде можно ограничиться метаданными + усечённым содержимым.


## Структура БД (DDL, PostgreSQL, минимальный вариант)
```sql
-- Пользователи
CREATE TABLE users (
    id              UUID PRIMARY KEY,
    email           TEXT UNIQUE,
    phone           TEXT UNIQUE,
    first_name     TEXT NOT NULL,
    last_name      TEXT NOT NULL,
    password_hash   TEXT,
    role            TEXT NOT NULL CHECK (role IN ('USER','FOREMAN','ADMIN')),
    status          TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','INACTIVE')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Рабочие
CREATE TABLE workers (
    id              UUID PRIMARY KEY,
    -- Если работник одновременно является зарегистрированным пользователем (например FOREMAN),
    -- то user_id связывает аккаунт и карточку рабочего.
    -- Для обычных рабочих user_id может быть NULL.
    user_id         UUID UNIQUE REFERENCES users(id),
    -- Карточка рабочего принадлежит конкретному FOREMAN (для "Мои рабочие" и переназначения).
    foreman_id      UUID NOT NULL REFERENCES users(id),
    first_name      TEXT NOT NULL,
    last_name       TEXT NOT NULL,
    position        TEXT,            -- опционально: должность для UI (мокапы); nullable
    status          TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','INACTIVE')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_workers_foreman ON workers(foreman_id);

-- Сессии (смены)
CREATE TABLE sessions (
    id              UUID PRIMARY KEY,
    worker_id       UUID NOT NULL REFERENCES workers(id),
    foreman_id      UUID NOT NULL REFERENCES users(id),
    start_at        TIMESTAMPTZ NOT NULL,
    end_at          TIMESTAMPTZ,
    status          TEXT NOT NULL CHECK (status IN ('ACTIVE','CLOSED')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_sessions_worker_active ON sessions(worker_id) WHERE status = 'ACTIVE';
CREATE INDEX idx_sessions_foreman ON sessions(foreman_id);
CREATE INDEX idx_sessions_time ON sessions(start_at, end_at);

-- Инвариант: у одного рабочего может быть только одна активная сессия.
CREATE UNIQUE INDEX ux_sessions_worker_active
    ON sessions(worker_id)
    WHERE status = 'ACTIVE';

-- Батчи синхронизации: хранятся только успешно применённые батчи (для идемпотентности).
-- При CONFLICT транзакция откатывается, запись не создаётся. Статус в БД не нужен: есть строка = батч применён.
CREATE TABLE sync_batches (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id),
    batch_uid       TEXT NOT NULL UNIQUE,  -- клиентский UUID батча; повтор запроса с тем же batch_uid = идемпотентный retry
    submitted_at    TIMESTAMPTZ NOT NULL,
    applied_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- События внутри батча (только сессии; управление рабочими — только через онлайн API)
CREATE TABLE sync_events (
    id              UUID PRIMARY KEY,
    batch_id        UUID NOT NULL REFERENCES sync_batches(id) ON DELETE CASCADE,
    type            TEXT NOT NULL CHECK (type IN ('START_SESSION', 'END_SESSION')),
    payload         JSONB NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_sync_events_batch ON sync_events(batch_id);

-- Опционально: сохранение «кривых» батчей (не применились из‑за CONFLICT), чтобы не терять данные.
-- Запись создаётся отдельной транзакцией после отката основной (не в той же транзакции, где применяли события).
CREATE TABLE failed_sync_batches (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    batch_uid       TEXT NOT NULL,              -- исходный batch_uid с клиента
    submitted_at    TIMESTAMPTZ NOT NULL,        -- когда клиент отправил (из тела запроса)
    events_snapshot JSONB NOT NULL,              -- полный массив events[] на момент ошибки
    failed_index    INT NOT NULL,                -- индекс события (0-based), на котором упали
    reason          TEXT NOT NULL,               -- причина (session already closed, worker not found, …)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_failed_sync_batches_user ON failed_sync_batches(user_id);
```

### Примечания по данным и бизнес-правилам
- При деактивации worker: закрыть активные sessions (end_at = now, status = CLOSED).
- Расчёт отработанных часов и `shiftEquivalent` для отчёта — на лету по `start_at`/`end_at` и деление на `shiftNormHours` (8); денормализованное поле `total_hours` в MVP не нужно.
- Смена = 8 часов (для будущих отчетов).
- Клиентское время: `start_at`/`end_at` в батчах передаются как значения с часовым поясом (ISO 8601, TIMESTAMPTZ). Backend принимает время **как есть** (источник истины — клиент), но может накладывать sanity‑чеки (например, отклонять события с абсурдно далёкой датой).

### Связь FOREMAN ↔ worker (чтобы бригадир тоже отмечал свои смены)

- Когда пользователь получает роль `FOREMAN` **через админский API** (`PATCH /api/v1/users/{id}` и т.п.) или в MVP вручную в БД, backend должен **создать или уже иметь** строку в `workers` для этого пользователя — т.е. выдача роли бригадира **неотделима** от появления соответствующей карточки в `workers` (в идеале в **одной транзакции** с обновлением `users.role`):
  - `workers.user_id = users.id` (т.е. карточка рабочего привязана к аккаунту бригадира),
  - `workers.foreman_id = users.id` (карточка попадает в список «Мои рабочие» этого же бригадира),
  - `workers.first_name` / `workers.last_name` копируются из `users.first_name` / `users.last_name`.
- Дальше бригадир отмечает свои смены так же, как и обычные рабочие:
  - UI использует `worker_id` этой карточки бригадира;
  - в батч отправляются события `START_SESSION`/`END_SESSION`,
  - `sessions.foreman_id` всегда соответствует пользователю, который записывает смену (аккаунт бригадира).

- **Обратное действие** (понижение / увольнение): см. подпункты **«Понижение с роли бригадира»** и **«Увольнение / блокировка»** в разделе **«Поведение ролей при регистрации»** — карточка бригадира в `workers` не удаляется ради истории, но **деактивируется** и **отвязывается** от аккаунта (`user_id = NULL`).

### Поток синхронизации (упрощенно)
- В батч входят **только события сессий**: START_SESSION, END_SESSION (рабочие **никогда** не в батчах — только `GET/POST/PATCH /workers` при наличии сети).
- **И при офлайне, и при онлайне** клиент не вызывает отдельных REST для старта/стопа смены: действия пользователя превращаются в события, попадают в **очередь батчей**, и при появлении сети батчи уходят на `POST /api/v1/sync/batch` **строго по порядку (head-of-line)** — новый батч не отправляется, пока предыдущий в очереди не принят сервером (**200**) или не обработан как **409** по политике клиента.
1) Клиент накапливает события старта/конца смен в локальной БД и формирует батчи с уникальным `batch_uid`; отправляет `POST /api/v1/sync/batch {batch_uid, events[]}` в порядке очереди.
2) Сервер в транзакции:
   - Проверяет уникальность batch_uid → идемпотентность.
   - Применяет события по порядку только к таблице sessions (worker_id в payload должен существовать и быть активным).
   - При конфликте — откат транзакции, запись в sync_batches не создаётся; опционально в отдельной транзакции сохраняем снимок батча в failed_sync_batches; ответ **409 Conflict** и в теле детали.
3) Ответ: **200 OK** — в БД добавлена строка в sync_batches и созданы/обновлены сессии, в теле — данные для кэша; **409 Conflict** — применения нет, в теле — детали ошибки; при включённом механизме — копия батча в failed_sync_batches для последующего редактирования/повтора.

#### Важно: `sessionId` (генерируется клиентом)
- Клиент **генерирует `sessionId` (UUID)** при нажатии «старт смены» и отправляет его в `START_SESSION.payload.sessionId`.
- Сервер создаёт запись `sessions.id = sessionId`, поэтому `END_SESSION` всегда закрывает смену по `sessionId` (в payload он **обязателен**).
- Это заменяет старую идею `clientSessionId` и позволяет безопасно разносить START/END по разным батчам при офлайне.

#### UX/офлайн: удобный “обед” без интернета
- Если пользователь нажал «стоп смены», но сети нет, клиент кладёт `END_SESSION` в очередь.
- **Локально** клиент сразу считает смену остановленной (карточка становится «🟢 Не работает»), чтобы бригадир мог **сразу же** начать новую смену (например, после обеда) даже в офлайне.
- Порядок событий на сервере сохраняется за счёт очереди (head-of-line): `START(sessionId1)` → `END(sessionId1)` → `START(sessionId2)` и т.д.
- Чтобы не нагенерить дублей `END_SESSION` при ошибках отправки, клиент ведёт локальный реестр **pending END по `sessionId`**: если `END_SESSION(sessionId=...)` уже в очереди, повторный “стоп” для этой же серверной сессии не добавляет второй END, а показывает пользователю сообщение «уже в очереди».

#### Серверное API для статуса (для корректного UI на нескольких устройствах)
- `GET /api/v1/sessions/active` (FOREMAN) — список активных сессий на сервере для текущего бригадира. Клиент может использовать это для подсветки активных работников даже если локальное состояние потеряно.

##### Офлайн-удобство: персистентный кэш активных сессий
- Чтобы бригадир мог **завершать смены офлайн** даже после перезапуска приложения, клиент хранит в DataStore последний успешный снимок `GET /api/v1/sessions/active` как `workerId -> sessionId` + `fetchedAt`.
- В офлайне UI отображает активность по правилу: **`merge(localSessions, cachedServerActive)`**.
- Если у worker есть активная смена **по кэшу**, то тап по карточке офлайн создаёт `END_SESSION(sessionId=...)` и локально убирает этого worker из `cachedServerActive`, чтобы карточка сразу стала «🟢 Не работает».

### Ошибка при обработке батча: как понимает фронт

- Обработка батча выполняется **в одной транзакции**: либо применяются все события, либо ни одно. Если ошибка на 9-м из 10 событий — откатываются и первые восемь; в БД не остаётся «частично применённого» батча.
- Запрос **синхронный**: клиент ждёт ответа в том же HTTP-запросе. Отдельной очереди или «узнаем позже» нет.
- **200 OK** — все события применены. В теле — созданные/обновлённые сессии (серверные id и т.п.) для обновления локального кэша.
- **409 Conflict** — при применении одного из событий произошла ошибка (сессия уже закрыта, worker не найден или деактивирован и т.п.). Батч целиком откатан. В теле:
  - `failedEventIndex` (0-based) — индекс события, на котором упали (например 8 для 9-го события);
  - `reason` — краткая причина («session already closed», «worker not found or inactive» и т.п.);
  - при необходимости: `failedEventType`, фрагмент `payload`, актуальное состояние сущности с сервера.
- По коду 409 и полям в теле фронт понимает, что батч не применён, на каком действии ошибка и что показать пользователю; при необходимости может сформировать новый батч (с новым batch_uid), исключив или скорректировав проблемное событие.

### Что происходит с батчем и как клиент переотправляет упавший батч

**На сервере при ошибке на 9-м событии**

- Вся транзакция откатывается: в БД не сохраняются ни события 1–8, ни запись о батче. Запись в `sync_batches` делается **только при успешном применении** (при коммите, ответ 200). При 409 коммита нет → строка с этим `batch_uid` не появляется, батч «не потреблён».
- Клиент получает ответ **409 Conflict** с телом `failedEventIndex: 8`, `reason: "…"` и при необходимости деталями по событию.

**На клиенте**

- **Ретраи при проблемах с сетью:** перед тем как помечать батч как неуспешный, клиент должен повторять запрос POST /sync/batch при сетевых ошибках (таймаут, обрыв соединения, 5xx) — например 2–3 попытки с экспоненциальной задержкой (backoff). Только после исчерпания ретраев считать, что «сеть подвела», и оставить батч в очереди на следующую сессию синхронизации или показать как ошибку сети (не как CONFLICT). Так из‑за кратковременных сбоев батч не попадает в «неуспешные» сразу.
- **Ответ 409 Conflict** — батч не применился из‑за бизнес-ошибки (сессия закрыта, worker не найден и т.п.). Ретраи здесь не помогают; клиент помечает батч как «неуспешный» (failed) и сохраняет детали из тела ответа для экрана «Неуспешные синхронизации».
- В локальной очереди батч не удаляется и не помечается как успешно синхронизированный, пока не получен **200 OK**.

**Как переобработать упавший батч**

1. **Исправить данные и отправить с тем же `batch_uid`**  
   - Убрать или скорректировать проблемное событие (например, 9-е: закрыть сессию, которой уже нет на сервере, или обновить `worker_id`).  
   - Сформировать новый список событий (8 или 9 штук) и отправить **тот же `batch_uid`** и новый `events[]`.  
   - Сервер не найдёт этот `batch_uid` в `sync_batches` (при прошлом 409 мы ничего не сохранили) и обработает запрос как первый раз. Если все события пройдут — вернёт **200 OK**, в БД появится запись в `sync_batches`, клиент помечает батч как успешно синхронизированный.

2. **Вариант с новым `batch_uid`**  
   - Удалить или исправить 9-е событие в локальной очереди.  
   - Создать **новый** `batch_uid` и отправить батч из оставшихся (или исправленных) событий.  
   - Идемпотентность сохраняется: каждый батч идентифицируется своим `batch_uid`; повторная отправка того же `batch_uid` после успешного применения вернёт **200 OK** и те же данные без повторного применения.

**Идемпотентность в двух сценариях**

- **Повтор из‑за сети** (ответ 200 потерялся): клиент снова шлёт тот же `batch_uid` и те же `events[]`. Сервер находит запись в `sync_batches` (батч уже был применён) и возвращает **200 OK** и те же данные, не применяя события заново.
- **Повтор после 409**: запись в `sync_batches` не создавалась, поэтому тот же или исправленный батч с тем же `batch_uid` обрабатывается как новый запрос.

### Что делать при 500 (и при таймауте/обрыве)

Пользователь отправил батч, в ответ пришла **500** (или таймаут, обрыв соединения). Неясно, применился ли батч на сервере: то ли транзакция откатилась, то ли применилась, но ответ не дошёл.

**Клиент**

1. **Ретрай с тем же телом** — тот же `batch_uid`, тот же `events[]`. Это безопасно:
   - если сервер не применил батч (откат перед 500) — при повторе батч применится и вернётся 200;
   - если сервер применил, но ответ потерялся или сервер упал после коммита — при повторе сервер найдёт `batch_uid` в `sync_batches` и вернёт **200 OK** и те же данные (идемпотентность), без повторного применения.
2. Повторять запрос **2–3 раза** с экспоненциальной задержкой (backoff). При первом же **200 OK** — пометить батч как успешно синхронизированный и выйти.
3. **После исчерпания ретраев** батч **не** помечаем как «неуспешный» (failed) — это не бизнес-ошибка, а временная. Оставляем его в очереди pending; при следующем запуске синхронизации (WorkManager, появление сети, ручное «синхронизировать») отправим снова. Можно показать пользователю: «Временная ошибка сервера, данные сохранятся при следующей синхронизации».

**Сервер**

- По возможности возвращать **500** только после отката транзакции (ничего не коммитить). Тогда при повторе батч гарантированно применится с нуля.
- Если успели закоммитить и затем упали — при повторе сработает проверка по `batch_uid`: запись уже есть → ответ 200 и те же данные. Дубликатов нет.

**Итог:** при 500/таймауте клиент ретраит тем же запросом; после ретраев батч остаётся в очереди и уйдёт при следующей синхронизации. В «Неуспешные синхронизации» такие батчи не попадают — туда только **409 Conflict**.

### Сохранение «кривого» батча: не терять и дать возможность отредактировать

Цель: батч, который не применился (409 Conflict), не терять; пользователь должен иметь возможность позже открыть его, поправить (например, убрать или изменить проблемное событие) и вручную отправить снова. Для этого используется **обязательная** таблица `failed_sync_batches` и локальное хранилище на клиенте.

**1. На клиенте (обязательно)**  
Перед отправкой батча — ретраи при сетевых ошибках (см. выше); в «неуспешные» попадают только батчи, по которым пришёл **409 Conflict** или после исчерпания ретраев так и не получили ответ. При ответе 409 клиент **не удаляет** батч из своей очереди. Он помечает его как «неуспешный» (failed) и сохраняет вместе с полем `failedEventIndex` и `reason` из ответа. В приложении можно сделать раздел «Неуспешные синхронизации»: список таких батчей, при открытии — показать события и место ошибки. Пользователь может отредактировать (удалить/изменить проблемное событие) и нажать «Отправить снова» — тогда формируется новый запрос (тот же или новый `batch_uid`) с исправленным `events[]`. Так батч не теряется и его можно переотправить после правки даже без доступа к серверному списку.

**2. На сервере (обязательно для 409)**  
Чтобы «кривой» батч был доступен и с другого устройства, и после переустановки приложения, бэкенд **всегда** сохраняет копию при первом ответе **409 Conflict**:

- После отката основной транзакции (применение событий не сохранилось) выполняется **отдельная транзакция**: INSERT в `failed_sync_batches` — сохраняем `user_id`, `batch_uid`, `submitted_at`, снимок `events[]` (`events_snapshot`), `failed_index`, `reason`. Так в БД появляется запись «такой-то батч не применился, вот его данные и причина».
- API: **GET /sync/failed-batches** — список таких записей для текущего пользователя (id, batch_uid, submitted_at, failed_index, reason; при необходимости в элементе списка или по отдельному запросу отдавать и `events_snapshot` для экрана редактирования). **DELETE /sync/failed-batches/{id}** — удалить запись после того, как пользователь успешно переотправил батч или решил отменить его.

**3. Сценарий «отредактировать и вручную сохранить»**  
- Пользователь видит уведомление или заходит в «Неуспешные синхронизации» (данные берутся с клиента и/или с GET /sync/failed-batches).  
- Открывает батч, видит события и причину ошибки (например, «событие 9: сессия уже закрыта»).  
- Редактирует: удаляет или правит 9-е событие (или правит привязку к worker/session).  
- Нажимает «Отправить снова». Клиент отправляет **новый** батч (новый `batch_uid` и исправленный `events[]`) на POST /sync/batch.  
- При успешном ответе **200 OK** клиент помечает локальный «неуспешный» батч как разрешённый; при включённом хранении на сервере можно вызвать DELETE /sync/failed-batches/{id} для соответствующей записи, чтобы не засорять список.

Итог: кривой батч не теряется (минимум — на клиенте, при необходимости и на сервере), его можно отредактировать и вручную переотправить; после успешного сохранения запись о неуспехе можно удалить.

### Чтобы зафейленный/ожидающий батч не терялся при «потере сессии»

Под «потерей сессии» имеется в виду закрытие приложения, смерть процесса, смена экрана — то есть когда данные в оперативной памяти теряются. Чтобы pending и failed батчи не пропадали:

**1. Хранить в постоянном хранилище на клиенте**  
Очередь pending-батчей и список «неуспешных» (failed) батчей должны лежать **не в памяти**, а в **постоянной локальной БД** (например Room): отдельные таблицы или поля с флагом статуса. Тогда при перезапуске приложения, убийстве процесса или смене активити данные остаются: при следующем запуске синхронизации подхватываются те же батчи, «Неуспешные синхронизации» показывают те же записи. Потеря «сессии» (экран/процесс) не приводит к потере зафейленного или ещё не отправленного запроса.

**2. Копия на сервере для 409 (опционально)**  
Если включено сохранение в `failed_sync_batches`, то при 409 Conflict батч дублируется на сервере. Тогда даже при **очистке данных приложения** или **переустановке** пользователь не теряет зафейленный батч: после входа можно вызвать GET /sync/failed-batches, получить список, открыть батч по `events_snapshot`, отредактировать и отправить снова. Рекомендуется включать этот механизм, если важно не терять неуспешные батчи при любых сценариях.

**3. Pending после 500/таймаута**  
Батчи, оставшиеся в очереди после исчерпания ретраев (500, таймаут), хранятся только на клиенте (в той же постоянной БД). При очистке данных или переустановке они теряются — на сервере копии нет (батч так и не был успешно применён). При необходимости в будущем можно ввести опциональное сохранение на сервере «неудачных попыток» (аналог failed_sync_batches для 500), но для MVP достаточно персистентной очереди на клиенте: пока пользователь не чистит данные приложения, pending-батчи сохраняются и уйдут при следующей синхронизации.

### Скорость: одна транзакция на батч

- Для типичного объёма (десятки событий в батче) одна транзакция выполняется быстро: каждое событие — один INSERT/UPDATE по `sessions`, без тяжёлой логики.
- Чтобы транзакция не растягивалась и не держала блокировки долго, на бэкенде стоит **ограничить размер батча** (например, не более 50–100 событий в одном запросе). При превышении — **400 Bad Request** с явным сообщением в теле; клиент может разбить очередь на несколько батчей (каждый со своим `batch_uid`). При таком лимите время ответа остаётся в пределах одной-двух секунд в нормальных условиях.
