# Веб-админка

## Решение

Для роли **ADMIN** планируется отдельный **веб-клиент** к существующему **REST API** (Ktor): тот же логин (JWT), тот же набор возможностей, что и в Android-приложении для администратора (отчёты, работники, ошибки синхронизации, табель и т.д. по мере реализации в API).

Нативное Windows-приложение **не** является целевым вариантом на первом этапе: один responsive web UI закрывает и **ПК**, и **мобильный браузер** (в т.ч. Safari на iPhone) без отдельной iOS-версии для админских задач.

## Развёртывание

**Целевой сценарий:** публикация во **внешнем интернете** (облако / VPS): HTTPS, домен, доступ админов из любой сети.

Альтернативы (локально / только LAN / VPN) остаются возможными технически, но для продукта зафиксирован приоритет **публичного доступа** с нормальной защитой (TLS, сильные пароли, при необходимости ограничение по IP или отдельный VPN поверх).

## Вёрстка и UX

- Один кодовый базис **адаптивной** вёрстки: десктоп и узкий экран (телефон).
- Широкие таблицы и отчёты на мобильном: закладывать **горизонтальную прокрутку**, упрощённые представления или карточки — без полного «второго макета», но с осознанной поддержкой маленьких экранов.

## Технические заметки (на этапе реализации)

- **CORS:** если origin фронта отличается от origin API — настроить на Ktor.
- **Токены:** веб обычно хранит сессию иначе, чем Android (`DataStore`); продумать access/refresh (в т.ч. `httpOnly` cookie или in-memory + refresh flow) согласно политике безопасности.
- **Код в репозитории:** отдельная директория (например `web/`) появится при старте разработки; в `PROJECT_STRUCTURE.md` будет обновлено дерево.

## Статус

Базовая реализация web-админки добавлена в `web/`:
- Login/logout с JWT+refresh
- Вкладки ADMIN: workers, users, reports, profile
- Отчёт по диапазону и скачивание `timesheet.xlsx`
- Основной UI-стиль проекта уже реализован именно здесь и должен считаться базовым направлением для дальнейшего дизайна продукта.

## Визуальный baseline

Текущая web-консоль фиксируется как **основной UI-референс проекта**.

Ключевые признаки:
- тёмный графитовый фон вместо светлого utility-стиля;
- золотой акцент как основной сигнал действия и статуса;
- крупная, более “product/premium” композиция: hero-блоки, панели, сильная навигация, статусные pill-элементы;
- dashboard-first подход для ADMIN, а не набор нейтральных CRUD-экранов;
- отчёты и таблицы выглядят как часть единой системы управления, а не как отдельные техничные формы.

## Последствия для Android

- Следующий редизайн Android должен визуально сближаться с web-консолью.
- Совпадать должны не только цвета, но и общий язык: контраст, форма карточек, навигация, статусные элементы, типографика и ощущение “операторской панели”.
- Старые mobile mockups полезны для сценариев и экранного состава, но не должны ограничивать обновление визуального стиля.
