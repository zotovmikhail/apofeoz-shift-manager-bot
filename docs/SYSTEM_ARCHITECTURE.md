# Общая архитектура Apofeoz

Этот документ даёт **целостный обзор системы** для людей и для агентского режима (Cursor/AI), а детальные детали по слоям описаны в:

- `docs/BACKEND_ARCHITECTURE.md` — архитектура backend на Kotlin
- `docs/MOBILE_ARCHITECTURE.md` — архитектура мобильных клиентов (Android + потенциальный iOS) и офлайн‑синхронизация
- `PROJECT_STRUCTURE.md` — физическая структура репозитория

## 1. Обзор системы

**MVP мобильного клиента и backend:** вход только по **паролю** (**саморегистрация** + login). Смены на сервер попадают **только через батчи** `POST /api/v1/sync/batch` в порядке очереди; рабочие — **только онлайн** через `/workers`.

Система состоит из компонентов:

- **Backend API (`backend/`, Kotlin)**  
  Централизованное хранилище и бизнес‑логика, REST API для мобильных клиентов.

- **Мобильные клиенты (Kotlin)**  
  - **Android приложение (`android/`)** — основной полевой клиент.
  - **Потенциальный iOS‑клиент (Kotlin Multiplatform Mobile)** — планируется как тонкий UI поверх общего KMM‑модуля.

- **База данных (PostgreSQL)**  
  Авторитетное хранилище пользователей, рабочих, сессий и батчей синхронизации.

Ключевые особенности:

- офлайн‑режим и пакетная синхронизация;
- роли пользователей (бригадир/админ).

## 2. Целевое разделение ответственности

- **Backend (`backend/`)**
  - авторизация и роли (FOREMAN, ADMIN);
  - управление рабочими и сессиями;
  - приём батчей синхронизации от мобильных клиентов с идемпотентностью и разрешением конфликтов;
  - отчёт по часам/сменам за вчера (ADMIN); аудит — при необходимости позже.

- **Мобильные приложения**
  - локальное хранилище (SQLite/Room/KMM‑Storage);
  - очередь офлайн‑операций;
  - удобный UX для бригадиров/админов (старт/стоп смен, управление рабочими, просмотр истории);
  - минимальная логика — всё, что можно, выносится в общий Kotlin‑код.

## 3. Мобильная архитектура и KMM

Подробности — в `MOBILE_ARCHITECTURE.md`. Здесь только общая картина.

### 3.1. Текущая цель

- Android‑приложение на **Kotlin + Jetpack Compose**, с офлайн‑режимом и синхронизацией через Backend.
- Модель данных и протокол синхронизации: рабочие — только через онлайн API; в офлайн‑батчах только события сессий (sync_batches, sync_events с типами START_SESSION, END_SESSION).

### 3.2. Возможность iOS‑клиента на Kotlin

Для поддержки iOS без полной переписи логики можно использовать **Kotlin Multiplatform Mobile (KMM)**:

- общий модуль `:shared` со слоями:
  - **domain** — бизнес‑модели и use‑cases, общие для Android и iOS;
  - **data** — источники данных, репозитории, клиент API, офлайн‑очередь и правила синхронизации;
  - **core** — общие утилиты (время, форматирование, маппинг ошибок, логика конфликтов).
- Android использует этот модуль как обычную зависимость.
- iOS получает тот же модуль как **Kotlin/Native framework**, который подключается в проект Xcode.

UI‑слой для iOS возможен в двух вариантах:

- **SwiftUI UI + Kotlin shared** (самый типовой путь);
- **Compose Multiplatform for iOS**, если потребуется максимальное переиспользование UI на Kotlin.

Для агентского режима важно:

- вся бизнес‑логика и модели должны быть **максимально вынесены в общий модуль**;
- платформо‑специфичный код (UI, доступ к системе, сетевой стек) должен быть чётко изолирован.

## 4. Backend архитектура (Kotlin)

Подробности — в `BACKEND_ARCHITECTURE.md`. Кратко:

- **Стек**: Kotlin + Ktor, PostgreSQL, Flyway, JWT.
- **Слои**:
  - `api` — контроллеры/роуты, фильтры безопасности;
  - `domain` — сервисы, доменные модели и правила;
  - `data` — репозитории, транзакции, миграции;
  - `utils` — инфраструктурные утилиты, валидация входных данных, работа со временем и т.п.
- **Ключевые сущности**:
  - `users`, `workers`, `sessions`, `sync_batches`, `sync_events` (таблицы devices и audit_log в MVP нет).
- **Синхронизация**:
  - приём батчей от клиентов (POST `/sync/batch`) — в батче только события сессий (START_SESSION, END_SESSION); управление рабочими — только через онлайн API. Идемпотентность по одному `batch_uid` на батч;
  - атомарное применение батча; ответ **200 OK** при успехе, **409 Conflict** при бизнес-конфликте;
  - возврат клиенту актуальных версий сущностей и описания конфликтов.

## 5. Потоки данных

### 5.1. Офлайн‑→ онлайн (мобильный клиент ↔ backend)

1. Пользователь офлайн фиксирует только старт/конец смен — события пишутся в локальную БД и в очередь батча. Добавление/редактирование/деактивация рабочих требуют сети.
2. Появляется интернет — планировщик (WorkManager/BackgroundTasks) инициирует синхронизацию.
3. Клиент формирует батч из событий сессий и отправляет на `/sync/batch`.
4. Backend обрабатывает батч в транзакции, помечая результат и возвращая актуальное состояние.
5. Клиент обновляет локальное состояние и статусы синхронизации.

## 6. Условности для агентского режима

Чтобы агенту было проще ориентироваться:

- **Основные точки входа в код**:
  - backend: `backend/src/main/kotlin/com/apofeoz/backend/…`
  - android: `android/app/src/main/java/com/apofeoz/shiftmanager/…`
  - (в будущем) общий KMM‑модуль: `shared/src/commonMain/kotlin/com/apofeoz/shared/…`

- **Где искать архитектуру и соглашения**:
  - общая картина: `docs/SYSTEM_ARCHITECTURE.md` (этот файл);
  - мобильные клиенты и синхронизация: `docs/MOBILE_ARCHITECTURE.md`;
  - backend и модель данных БД: `docs/BACKEND_ARCHITECTURE.md`;
  - структура репозитория: `PROJECT_STRUCTURE.md`.

- **Общие принципы**:
  - бизнес‑логика — в domain/общем KMM‑модуле, а не в UI;
  - все операции, затрагивающие синхронизацию, должны быть идемпотентными со стороны backend;
  - идентификаторы сущностей на сервере — UUID, на клиенте допускаются временные localId для офлайн‑режима.
